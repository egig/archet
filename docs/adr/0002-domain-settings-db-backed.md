# Domain Settings are DB-backed and console-editable, not static config

Business logic pipelines need per-Domain runtime values (e.g. an `auth` domain's session TTL). The obvious-looking alternative was to extend `FrameworkConfig` (`src/core/config.ts`) with a per-domain section, versioned in code and baked in at build/deploy time like everything else `defineConfig()` covers. We chose a separate, DB-backed store instead: Domain Settings live in Postgres, scoped per Domain, and are editable from the console without a redeploy. This trades away config-as-code (no git history per change, no code review on a settings change) for the thing business logic actually needs — an operator adjusting a business rule (e.g. a discount threshold) at runtime, the same way they'd edit any other record through the console. It also means Domain Settings need their own typed schema and validation, similar in shape to a Model's fields, rather than reusing plain TypeScript interface typing.
